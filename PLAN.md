# План доведения системы до production-quality

Документ — не для маркетинга, а для принятия решений. Цель: довести
систему до состояния, когда:

1. **Никто не может войти под чужой ролью**, даже если знает email коллеги.
2. **Пароли не лежат открытым текстом** ни в коде, ни в базе.
3. **TypeScript не ругается** — расхождения моделей не маскируют баги.
4. **Билд не тащит лишнего** — страница открывается быстро.
5. **Большие файлы** разбиты так, что в них можно ориентироваться.

Текущее состояние и оставшаяся работа — ниже. Каждый блок: что меняется,
что видит пользователь, как откатить.

## 1. Безопасность: миграция на Supabase Auth (БОЛЬШОЙ ЭТАП)

**Зачем:** Сейчас «авторизация» — это:
1. Хардкодные демо-юзеры с открытыми паролями (закрыто env-флагом).
2. Сотрудники из таблицы `employees` с **открытым паролем в БД**, сверка
   на клиенте.
3. Сервер `server.js` принимает любые `x-user-*` заголовки на веру.
4. RLS-политики в Supabase почти везде — `USING (true)`, потому что
   `auth.uid()` всегда `null` (фронт ходит как anon).

Это значит, что **любой человек с доступом к базе видит все пароли**, и
любой пользователь, открыв DevTools, может подделать любую роль.

### Что увидят сотрудники

**День X — сразу после деплоя:**
Каждый сотрудник один раз заходит, видит экран «Установите новый
пароль», получает на почту ссылку, кликает, задаёт пароль. После этого
вход работает как раньше — email + пароль.

**День X+1:**
Всё работает как и раньше, только без дыр.

### План по фазам

#### Фаза 1.1 — подготовка инфраструктуры (без эффекта для пользователей)

1. В Supabase Dashboard включить **Email/Password Auth provider**
   (вероятно уже включено по умолчанию).
2. Настроить **email templates** для «Reset password» / «Invite user»
   — на русском, с брендингом RB Partners.
3. Подключить SMTP в Supabase Auth (можно через тот же SMTP, что в
   `SMTPSettings.tsx`).
4. Завести один тестовый аккаунт в Supabase Auth и убедиться, что
   reset-flow работает.

**Rollback:** не нужен — никаких изменений в боевой системе.

#### Фаза 1.2 — миграция существующих сотрудников

1. Из таблицы `employees` для каждой записи с email **создать
   пользователя в Supabase Auth** через admin API (Service Role Key):
   `supabase.auth.admin.createUser({ email, email_confirm: true,
   password: <случайный 32-символьный пароль>, user_metadata: { role,
   level, name, department, position } })`.
2. Этот шаг можно прогнать одним SQL-/TS-скриптом, локально, по списку.
3. На email каждого сотрудника отправить ссылку «Установите пароль»
   (`supabase.auth.admin.generateLink({ type: 'invite', email })`).
4. **Колонку `employees.password` НЕ удалять** на этом этапе — она
   нужна как fallback, пока не все ввели новый пароль.

**Что видит сотрудник:** письмо «Вам нужно установить пароль для
работы в RB Suite. Ссылка ниже действует 7 дней».

**Rollback:** Supabase-юзера можно удалить, `employees.password`
остаётся как был — старая логика продолжает работать.

#### Фаза 1.3 — переключение фронта на Supabase Auth

В `src/contexts/AuthContext.tsx` `login()` больше не использует публичные тестовые аккаунты. Следующий шаг — заменить проверку пароля из `employees` на Supabase Auth:

```ts
const { data, error } = await supabase.auth.signInWithPassword({
  email, password,
});
if (error || !data.session) return false;
// user_metadata из Supabase → User
const meta = data.user.user_metadata;
const user: User = {
  id: data.user.id,
  email: data.user.email!,
  name: meta.name,
  role: normalizeUserRole(meta.role, meta.level),
  // ...
};
setUser(await enrichUserWithAccess(user));
```

Сессию Supabase хранит сам (в `localStorage` под своим ключом). Свой
`localStorage.setItem('user', ...)` можно убрать или оставить как кеш
для быстрого ререндера до первого `getSession()`.

В `logout()` — `supabase.auth.signOut()`.

**Что видит сотрудник:** ничего нового; вход работает как раньше, но
теперь через Supabase. Сессия валидна 1 час с автоматическим refresh.

**Rollback:** вернуть прежний `login()` (один commit).

#### Фаза 1.4 — переключение `server.js` на JWT

В `server.js` сейчас `getUserFromRequest` доверяет заголовкам
`x-user-*`. Заменить на:

```js
import { createClient } from '@supabase/supabase-js';
const supabase = createClient(SUPABASE_URL, SUPABASE_ANON_KEY);

async function getUserFromRequest(req) {
  const auth = req.headers.authorization;
  if (!auth?.startsWith('Bearer ')) return null;
  const token = auth.slice(7);
  const { data, error } = await supabase.auth.getUser(token);
  if (error || !data.user) return null;
  return data.user;
}
```

Фронт должен прикладывать `Authorization: Bearer ${session.access_token}`
ко всем `fetch('/api/...')` — это одно место в `src/lib/api.ts` (если
есть) или fetch-обёртка.

На `/api/files/:projectId/:filename` и `/api/project-data/:projectId`
добавить проверку: «у этого пользователя есть доступ к проекту?».
Сделать через RPC `has_project_access(project_id, user_id)` или
прямой SELECT по `project_team`/`project_participants`.

**Rollback:** убрать проверку JWT, вернуть старый `getUserFromRequest`.

#### Фаза 1.5 — ужесточение RLS (требует Фазы 1.3 и 1.4)

Теперь `auth.uid()` ВАЖЕН и не равен `null`. Можно переписать политики
с `USING (true)` на:

- **employees**: чтение видит только сам пользователь + HR/CEO/admin.
- **projects**: SELECT — только участники команды + руководство;
  INSERT/UPDATE — только procurement/admin; DELETE — только CEO/admin.
- **timesheets**: SELECT — только свои + руководство; INSERT — только
  свои.
- **app_settings**: SELECT для всех authenticated; UPDATE только для
  admin.
- **attendance**, **project_survey_*** — аналогично.

Каждую таблицу — отдельной миграцией с явным DROP старой политики и
CREATE новой. Проходить по одной таблице, после каждой миграции
проверять на стенде, что нужные роли видят/могут делать то, что
ожидается.

**Rollback:** для каждой таблицы — отдельная revert-миграция, которая
ставит `USING (true)` обратно.

#### Фаза 1.6 — удаление старого кода

Когда все сотрудники зашли через Supabase (отслеживается по последнему
`auth.users.last_sign_in_at`):

1. Удалить колонку `employees.password` (миграция).
2. Удалить fallback на `employees`-логин в `login()` после миграции на Supabase Auth.

**Не делать раньше:** иначе сотрудник, не успевший установить пароль,
заблокирован.

### Сколько по времени

| Фаза | Эффорт | Можно ли делать в рабочее время |
|------|--------|----------------------------------|
| 1.1 Инфра | 1–2 часа | Да |
| 1.2 Миграция учёток | 2–4 часа + рассылка | Да, без даунтайма |
| 1.3 Фронт на Supabase Auth | 4–8 часов + тест | Желательно вечером |
| 1.4 Server JWT | 2–4 часа | Вместе с 1.3 |
| 1.5 RLS — по таблице | 30 мин на таблицу × ~10 таблиц | Постепенно, неделями |
| 1.6 Зачистка | 1 час | После того как все вошли |

Итого: **5–7 рабочих дней** реальной работы, **2–3 недели** календарных
с учётом ожидания всех пользователей.

## 2. Типы: убрать ругань TypeScript (СРЕДНИЙ ЭТАП)

**Зачем:** Сейчас `tsc --noEmit` показывает **218 ошибок**. Большая
часть — потому что в проекте **7 разных определений типа `Project`**:

- `src/types/project.ts` — основной (используется в большинстве страниц)
- `src/types/project-simple.ts` — упрощённый
- `src/types/index.ts` — устаревший
- `src/lib/dataStore.ts`, `src/lib/supabaseDataStore.ts`,
  `src/store/dataStore.ts` — внутренние типы датасторов
- `src/hooks/useProjects.ts` — расширение Supabase-типа

И они не совпадают. Например, `Project.companyName` есть в одном
определении, нет в другом — отсюда десятки ошибок «Property
'companyName' does not exist».

### Что меняется

**Только код**, на UI ничего не влияет.

### План

1. **Аудит:** какое определение `Project` реально используется в
   страницах. По grep видно, что доминирует `src/types/project.ts`.
2. **Выбор каноничного типа** — `src/types/project.ts`. Сделать его
   superset из всех 7 (добавить недостающие поля).
3. **Удалить остальные 6** или превратить их в `type Project = import('./project').Project` (transition).
4. **Обновить datastores** — `dataStore.ts` и `supabaseDataStore.ts`
   должны возвращать тот же тип, что и `useSupabaseData`.
5. **Прогнать `tsc`** — починить оставшиеся точечные ошибки.

### Сколько по времени

- Аудит и выбор: 1–2 часа.
- Унификация: 4–8 часов.
- Прогон tsc + точечные баги: 2–4 часа.

Итого: **2 рабочих дня**.

### Риск

Средний. Можно проглядеть место, где использовался какой-то
устаревший тип в специфичной форме. Митигация — после каждой группы
изменений: build + ручной прогон ключевых сценариев (создание проекта,
редактирование, утверждение).

## Что НЕ нужно делать

- **Не переходить на bcrypt в `employees.password`** — это плохой
  компромисс между «открытым текстом» и «нормальной auth». Сразу
  Supabase Auth.
- **Не закрывать RLS до перевода фронта на Supabase Auth** — все
  логины сломаются.
- **Не разбивать большие файлы прямо сейчас** — пока модели
  (Project в первую очередь) не унифицированы, придётся разносить
  одно и то же повторно.
- **Не пытаться сделать всё одним PR** — каждая фаза = отдельный
  PR с возможностью отката.
