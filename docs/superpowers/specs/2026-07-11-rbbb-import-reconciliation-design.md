# RBBB Import Reconciliation Design

**Дата:** 2026-07-11

**Статус:** утверждён пользователем

**Ветка:** `codex/rbbb-recovery-2026-07-11`

## 1. Цель

Создать воспроизводимый read-only контур сверки исторических импортов RBBB, который связывает исходные Excel-файлы, сохранённые отчёты и текущее состояние live Supabase. Результатом этапа должен стать единый проверяемый реестр решений, а не новый импорт.

Контур должен отдельно разобрать:

- 66 конфликтных строк RBI;
- 123 строки RBI без найденного проекта;
- 5 ненайденных проектов из реестра Кенжекулова;
- фактическое состояние файлов `Аманов Онгар.xlsx`, `Бадамбаева Сауле(1).xlsx`, `Сартаева Гаухар(1).xlsx`;
- смешение нескольких partner-ledger запусков под общими marker-значениями.

## 2. Зафиксированные ограничения

- Live-БД на этом этапе доступна только через `SELECT`.
- Нельзя повторно запускать существующие import/commit/cleanup scripts.
- 66 RBI conflicts и 123 RBI not-found не применяются автоматически.
- Новые проекты создаются только после отдельного утверждения пользователем.
- Таблица `bonuses` не заполняется, выплаты не создаются.
- Корневые Excel-файлы нельзя считать идентичными импортированным версиям только по имени.
- Неизвестные или неоднозначные строки получают явный статус review; отсутствие доказательства не превращается в положительное совпадение.

## 3. Подтверждённая исходная точка

Live-аудит `2026-07-11T14:43:27.486Z` подтвердил:

- 1043 проекта;
- 140 сотрудников;
- 14629 approved timesheet rows на 110364,4 часа;
- RBI marker на 144 проектах;
- RBI `assignedBy` marker у 152 участников;
- 0 повторяющихся пар `employee + role` внутри RBI-команд;
- 64 проекта с общим partner-ledger marker;
- 839 approved timesheet rows с общим partner-ledger approval marker на 6233,8 часа;
- 0 строк в `bonuses`, `project_team`, `project_participants`;
- 0 неразбираемых `projects.notes`.

Сохранённый RBI dry-run содержит 467 исходных строк:

- 228 exact;
- 50 probable;
- 66 conflict;
- 123 not-found;
- 833 сопоставленных участника;
- 268 предложенных добавлений;
- 384 уже существовавших участника;
- 12 external/GPH записей.

Live batch `2026-06-04-drive-bulk-v3` содержит 14653 timesheet rows. По трём спорным сотрудникам подтверждено:

| Сотрудник | Live rows | Live hours | Статусы |
|---|---:|---:|---|
| Аманов Онгар | 385 | 3072 | 382 approved, 3 submitted |
| Сауле Бадамбаева | 535 | 3734 | 530 approved, 5 submitted |
| Сартаева Гаухар Шыныбековна | 452 batch rows / 471 всего | 3179 batch hours / 3387 всего | 450 approved, 19 draft, 2 submitted |

Корневые книги и копии в `tmp/timesheets-raw` имеют разные SHA-256 и разные размеры используемых диапазонов. Поэтому факт наличия live-строк подтверждает обработку Drive/batch версии, но не доказывает построчную обработку каждого корневого файла.

## 4. Выбранный подход

Используется evidence-first offline reconciliation.

Отдельный read-only сборщик строит нормализованный набор строк сверки и создаёт два согласованных артефакта:

1. JSON — машиночитаемое доказательство и вход для тестов.
2. XLSX — пользовательский реестр для принятия решений.

Сборщик ничего не применяет. Будущий apply-контур проектируется отдельно после заполнения и утверждения реестра.

Не выбранные подходы:

- немедленная очередь конфликтов внутри `/projects`: отложена до стабилизации данных;
- автоматическое создание проектов по score: отклонено из-за риска дублей и неверных периодов;
- доверие только marker-полям: отклонено, потому что partner-ledger marker переиспользовался несколькими запусками.

## 5. Архитектура

### 5.1 Источники

Сборщик читает:

- `reports/rbi-project-enrichment-dryrun/dryrun.json`;
- `reports/rbi-project-enrichment-dryrun/commit-results.json`;
- `reports/rbi-project-enrichment-dryrun/people-add-results.json`;
- `reports/kenzhekulov-projects/analysis.json`;
- `reports/partner-ledger-close/partner-ledger-close-report.json` только как историческое доказательство, не как текущий source of truth;
- `tmp/reimport-drafts.json`;
- пять названных корневых Excel-файлов и соответствующие доступные raw/Drive версии;
- live `projects`, `employees`, `timesheet_entries` через paginated `SELECT`.

### 5.2 Стабильная идентичность строки

Каждая исходная строка получает `sourceKey`:

```text
normalized-file-name :: normalized-sheet-name :: source-row-number
```

Для timesheet-строк дополнительно строится `rowFingerprint`:

```text
employee-id :: work-date :: rounded-hours :: normalized-project-name :: normalized-notes
```

Если исходная версия не содержит employee ID, применяется подтверждённое отображение имени на live employee. Неоднозначное отображение получает review-статус и не участвует в автоматическом доказательстве импорта.

### 5.3 Классификация

Каждая строка получает ровно один итоговый статус:

- `confirmed_applied` — live-данные и marker/evidence однозначно подтверждают применение;
- `needs_project_match` — есть несколько правдоподобных live-кандидатов;
- `team_conflict` — проект найден, но Excel и live-команда расходятся;
- `create_candidate` — live-кандидат с достаточным score не найден, при этом строка содержит непустое нормализованное имя клиента длиной не менее четырёх символов и хотя бы один контекстный признак: тип аудита, период или наша компания;
- `skip_candidate` — строка является дублем, заголовком, служебной записью или не должна создавать проект;
- `external_person` — GPH/external участник не должен автоматически становиться внутренним employee;
- `source_version_mismatch` — проверяемый локальный файл не совпадает с версией, доказанной import batch;
- `insufficient_evidence` — данных недостаточно для решения.

Статус `create_candidate` является предложением, а не разрешением на запись.
Строки без указанного минимального набора полей получают `insufficient_evidence`, а не `create_candidate`.

### 5.4 RBI

Для всех 189 unresolved RBI rows сборщик повторно оценивает кандидатов против текущего live набора проектов, не используя результаты старого score как окончательную истину.

Для сопоставимости с историческим dry-run сохраняются исходные границы классификации: score ниже 65 означает отсутствие кандидата; score от 82 при отрыве не менее 10 означает probable; score от 105 при отрыве не менее 12 означает exact; остальные найденные варианты являются conflict. Сборщик хранит и старую, и повторно вычисленную классификацию, а изменение класса выделяет как отдельное расхождение.

Реестр хранит:

- исходный клиент, тип аудита, период и компания;
- старый best/second candidate и score;
- текущие live candidates;
- существующую live-команду;
- предложенную Excel-команду;
- точное описание конфликта;
- рекомендуемое действие;
- пустые поля `decision`, `approvedProjectId`, `reviewComment` для ручного решения.

### 5.5 Кенжекулов

Набор Кенжекулова восстанавливается по исходной книге и source-specific evidence. Общие значения:

- `auto:partner-ledger-close-2026-06-09`;
- `auto:partner-ledger-timesheet-approval-2026-06-09`

не считаются достаточными для отнесения строки именно к Кенжекулову.

Сборщик должен:

- восстановить 52 строки исходной книги;
- показать исторические 47 обработанных строк / 41 уникальный проект как заявленный результат;
- найти live-доказательство по каждому проекту и участнику;
- отдельно вывести `БОЗОЙ`, `АО КТК`, `Мирбуш`, `ТОО ТИМ`, `ТОО TGAlfarabi`;
- не считать агрегат 64/839 специфичным для Кенжекулова;
- пометить строки без source-specific evidence как `insufficient_evidence`.

### 5.6 Три спорных timesheet-файла

Для каждой пары root/raw/Drive версия вычисляются:

- SHA-256 файла;
- листы и используемые диапазоны;
- количество валидных timesheet-строк;
- сумма часов;
- минимальная и максимальная дата;
- fingerprint set;
- сколько fingerprints найдено в live batch v3;
- сколько присутствует только в root, только в raw/Drive и только в live.

Итог должен различать:

- «сотрудник присутствует в live batch»;
- «эта конкретная версия файла полностью импортирована».

## 6. Выходной Excel-реестр

Рабочая книга содержит листы:

1. `Summary` — контрольные суммы и список блокирующих решений.
2. `RBI Conflicts` — 66 конфликтных строк.
3. `RBI Not Found` — 123 ненайденные строки.
4. `Kenzhekulov` — все строки исходного реестра и live evidence.
5. `Timesheet Files` — сравнение трёх root-файлов с импортированными версиями.
6. `External People` — GPH/external записи.
7. `Data Dictionary` — определения статусов и допустимых решений.

Колонки решений используют фиксированные значения:

- `use_existing_project`;
- `create_new_project`;
- `keep_live_team`;
- `apply_excel_team`;
- `merge_team_manually`;
- `keep_external`;
- `skip`;
- пусто — решение не принято.

Книга является review-артефактом. Изменение значения в Excel не меняет live-БД.

## 7. Безопасность

- Source-level тест запрещает `.insert(`, `.update(`, `.upsert(`, `.delete(`, `.rpc(` и `--commit` в read-only сборщике.
- Скрипт завершается с ошибкой при отсутствии read credentials, обязательного source-файла или неожиданной структуры отчёта.
- Все обращения к таблицам пагинируются.
- Секреты и Supabase keys не записываются в отчёты.
- Каждый запуск создаёт timestamped JSON/XLSX и не перезаписывает предыдущий результат.
- Ни один существующий import/cleanup script не вызывается из сборщика.

## 8. Проверки качества

Автоматические проверки должны подтверждать:

- 467 RBI source rows и разбиение 228/50/66/123 в исходном отчёте;
- ровно 66 строк на листе `RBI Conflicts`;
- ровно 123 строки на листе `RBI Not Found`;
- стабильность `sourceKey` и `rowFingerprint`;
- отсутствие запрещённых mutation calls;
- согласованность JSON и Excel summary;
- отсутствие формульных ошибок в созданной книге;
- сохранение Unicode-имён без mojibake;
- повторный read-only запуск создаёт эквивалентные данные за исключением timestamp и наблюдаемых внешних изменений.

После реализации повторно выполняются `typecheck`, unit tests, Node tests и build.

## 9. Граница этапа

Этап завершается, когда создан проверенный read-only JSON/XLSX реестр и все строки имеют доказательство, классификацию и рекомендуемое действие.

В этап не входят:

- создание или обновление live-проектов;
- изменение live-команд;
- повторный импорт timesheet;
- approval/rejection timesheet;
- создание бонусов или выплат;
- production deployment.

После ручного заполнения решений проектируется отдельный apply-процесс с dry-run по умолчанию, allowlist утверждённых `sourceKey` и собственным rollback/evidence отчётом.
